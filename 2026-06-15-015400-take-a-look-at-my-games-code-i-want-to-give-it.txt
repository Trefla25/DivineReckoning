  Are your core choices good?

  Yes, mostly. For an isometric point-and-click action roguelike:

  - NavMeshAgent for click-to-move — correct and efficient. This is the standard
  Diablo/ARPG approach. Keep it.
  - Click-to-target → auto-walk-into-range → attack — good pattern for this
  genre. Keep the flow.
  - Animation events for footsteps (in CharacterAudio) — you already use the
  right tool here. We'll lean on this more.

  Two things you're doing that I'd change:

  1. Invoke(nameof(SendAttack), attackDelay) with magic timing. This decouples
  the damage from the actual animation. If you change the attack animation, the
  hit lands at the wrong frame. Since you already use animation events, the
  attack hit should fire from an animation event on the attack clip — not a
  hardcoded 0.3f.
  2. animator.Play(STRING) every frame + Invoke-based busy reset. The playerBusy
  bool is really a tiny state machine in disguise. As you add
  abilities/dodges/death, this will sprawl. Promote it to an explicit state
  machine now while it's cheap.

  The core problem

  Character is a god class doing six jobs: input wiring, movement, targeting,
  combat, animation, and VFX. That's exactly what you want to split. The class
  is even named Character but lives in PlayerController.cs — that mismatch is a
  symptom.

  Target architecture (composition, not inheritance)

  The idiomatic Unity approach is small components on the same GameObject,
  coordinated by one thin brain. Don't build a deep inheritance tree.

  Player (GameObject)
  ├── PlayerController      ← thin orchestrator + state machine (the "brain")
  ├── PlayerInput          ← wraps CustomInputs, raises C# events
  ├── PlayerMotor          ← owns NavMeshAgent: MoveTo(point),
  FaceMoveDirection, IsMoving
  ├── PlayerTargeting      ← raycast, resolves Interactable, holds CurrentTarget
  ├── PlayerCombat         ← attack timing, range check, damage, attack VFX
  ├── PlayerAnimator       ← wraps Animator: PlayIdle/Walk/Attack/Pickup
  (hashes)
  └── CharacterAudio       ← (already exists)

  Responsibility split, mapped from your current methods:

  ┌──────────────────┬───────────────────────────────────────────────────────┐
  │  New component   │                Absorbs from Character                 │
  ├──────────────────┼───────────────────────────────────────────────────────┤

  Step 1 — Extract PlayerAnimator (lowest risk first)

  Pure wrapper, no game logic. Use cached hashes instead of string Play each
  frame.

  public class PlayerAnimator : MonoBehaviour
  {
      static readonly int Idle   = Animator.StringToHash("Idle");
      static readonly int Walk   = Animator.StringToHash("Walk");
      static readonly int Attack = Animator.StringToHash("Attack");
      static readonly int Pickup = Animator.StringToHash("Pickup");

      Animator animator;
      void Awake() => animator = GetComponent<Animator>();

      public void PlayIdle()   => animator.Play(Idle);
      public void PlayWalk()   => animator.Play(Walk);
      public void PlayAttack() => animator.Play(Attack);
      public void PlayPickup() => animator.Play(Pickup);
  }
  Replace animator.Play(WALK) etc. in Character with playerAnimator.PlayWalk().

  Step 2 — Extract PlayerMotor

  Owns the NavMeshAgent. Pure "how to move," no decision-making.

  [RequireComponent(typeof(NavMeshAgent))]
  public class PlayerMotor : MonoBehaviour
  {
      [SerializeField] float lookRotationSpeed = 8f;
      NavMeshAgent agent;
      void Awake() => agent = GetComponent<NavMeshAgent>();

      public bool IsMoving => agent.velocity.sqrMagnitude > 0.001f;
      public void MoveTo(Vector3 point) => agent.SetDestination(point);
      public void Stop() => agent.SetDestination(transform.position);

      public void FaceMoveDirection()
      {
          Vector3 dir = agent.desiredVelocity;
          Vector3 flat = new(dir.x, 0, dir.z);
          if (flat.sqrMagnitude < 0.001f) return;
          transform.rotation = Quaternion.Slerp(
              transform.rotation, Quaternion.LookRotation(flat),
              Time.deltaTime * lookRotationSpeed);
      }
  }

  Step 3 — Extract PlayerInput

  Wrap CustomInputs and expose plain C# events. This keeps the generated input
  class out of your gameplay code.

  public class PlayerInput : MonoBehaviour
  {
      public event Action MoveClickPerformed;
      public bool MoveHeld => input.Main.MoveClick.IsPressed();

      CustomInputs input;
      void Awake() { input = new CustomInputs(); input.Main.MoveClick.performed
  += _ => MoveClickPerformed?.Invoke(); }
      void OnEnable()  => input.Enable();
      void OnDisable() => input.Disable();
  }

  Step 4 — Extract PlayerTargeting

  Owns the raycast and CurrentTarget. Decides what you clicked; doesn't move or
  attack.

  public class PlayerTargeting : MonoBehaviour
  {
      [SerializeField] LayerMask clickableLayers;
      [SerializeField] ParticleSystem clickEffect;

      public Interactable CurrentTarget { get; private set; }

      // returns true if a ground point was clicked (vs an interactable)
      public bool TryResolveClick(bool spawnEffect, out Vector3 groundPoint)
      {
          groundPoint = default;
          Vector2 mouse = Mouse.current.position.ReadValue();
          if (!Physics.Raycast(Camera.main.ScreenPointToRay(mouse), out var hit,
  100, clickableLayers))
              return false;

          if (spawnEffect && clickEffect) Instantiate(clickEffect, hit.point +
  Vector3.up * 0.1f, clickEffect.transform.rotation);

          if (hit.transform.CompareTag("Interactable")) { CurrentTarget =
  hit.transform.GetComponent<Interactable>(); return false; }
          CurrentTarget = null; groundPoint = hit.point; return true;
      }
      public void ClearTarget() => CurrentTarget = null;
  }

  Step 5 — Extract PlayerCombat

  All attack* fields + the hit logic. Key fix: fire the actual hit from an
  animation event, not Invoke.

  public class PlayerCombat : MonoBehaviour
  {
      [SerializeField] float attackRange = 1.5f;
      [SerializeField] int attackDamage = 1;
      [SerializeField] ParticleSystem attackEffect;

      public float AttackRange => attackRange;
      Interactable target;

      public void BeginAttack(Interactable t) => target = t;   // called by 
  controller

      // Hook this to an Animation Event on the attack clip's hit frame:
      public void AnimationHit()
      {
          if (target == null || target.damageActor == null ||
  target.damageActor.currentHealth <= 0) return;
          if (attackEffect) Instantiate(attackEffect, target.transform.position
  + Vector3.up, Quaternion.identity);
          target.damageActor.TakeDamage(attackDamage);   // reuse cached actor, 
  no second GetComponent
      }
  }
  (Note: this drops the redundant currentTarget.GetComponent<DealDamageActor>()
  on line 170 — you already cache damageActor in Interactable.)

  Step 6 — Reduce PlayerController to an orchestrator + state machine

  It now only coordinates. Replace playerBusy with explicit states.

  public enum PlayerState { Idle, Moving, Attacking, Interacting, Dead }

  [RequireComponent(typeof(PlayerMotor), typeof(PlayerTargeting), 
  typeof(PlayerCombat))]
  public class PlayerController : MonoBehaviour
  {
      PlayerInput input; PlayerMotor motor; PlayerTargeting targeting;
      PlayerCombat combat; PlayerAnimator anim;
      PlayerState state = PlayerState.Idle;

      void Awake() { /* GetComponent each; */ }
      void OnEnable()  => input.MoveClickPerformed += OnMoveClick;
      void OnDisable() => input.MoveClickPerformed -= OnMoveClick;

      void OnMoveClick()
      {
          if (state == PlayerState.Attacking || state ==
  PlayerState.Interacting) return;
          if (targeting.TryResolveClick(true, out var point))
  motor.MoveTo(point);
      }

      void Update()
      {
          if (state == PlayerState.Attacking || state ==
  PlayerState.Interacting) return;

          // hold-to-move
          if (input.MoveHeld && targeting.TryResolveClick(false, out var p))
  motor.MoveTo(p);

          // chase + engage target
          var target = targeting.CurrentTarget;
          if (target && Vector3.Distance(target.transform.position,
  transform.position) <= combat.AttackRange)
              Engage(target);
          else if (target) motor.MoveTo(target.transform.position);

          motor.FaceMoveDirection();
          anim.SetMovement(motor.IsMoving);   // Idle/Walk
      }

      void Engage(Interactable t)
      {
          motor.Stop();
          if (t.interactableType == InteractableType.Enemy)
          { state = PlayerState.Attacking; combat.BeginAttack(t);
  anim.PlayAttack(); }
          else
          { state = PlayerState.Interacting; t.InteractWithItem();
  targeting.ClearTarget(); anim.PlayPickup(); }
      }

      // Hook to an Animation Event at the END of attack/pickup clips:
      public void OnActionFinished() => state = PlayerState.Idle;
  }

  The OnActionFinished() animation event replaces your
  Invoke(nameof(ResetBusyState), attackSpeed) magic number — the state resets
  exactly when the animation ends.

  Efficiency notes (your specific code)

  - Camera.main every raycast — Camera.main does a FindGameObjectWithTag
  internally. Cache it once in PlayerTargeting.Awake().
  - Duplicate GetComponent<DealDamageActor>() (line 170) — you already store
  damageActor on Interactable. Use it; drop the second lookup.
  - SetAnimations() calling Play every frame — switching to a SetMovement(bool)
  that only plays on change avoids redundant calls (cheap, but cleaner).
  String→hash caching (Step 1) also helps.
  - DealDamageActor.Death() is public and destroys the GameObject — fine, but
  your SendAttack null-checks currentHealth <= 0 after the enemy may already be
  destroyed. The state-machine + animation-event flow above sidesteps the race.

  How this sets you up for abilities / deckbuilding (brief)

  This is the payoff. Once PlayerCombat exists, the basic attack becomes just 
  one ability. Later:

  - Define abilities as ScriptableObjects (AbilitySO: cooldown, range,
  animation, effect). Your "deck" is a List<AbilitySO>.
  - Add an AbilitySystem component that holds the equipped abilities and a
  UseAbility(slot) method, which drives PlayerCombat + PlayerAnimator the same
  way basic attack does now.
  - The PlayerState enum gains UsingAbility; the orchestration pattern doesn't
  change.

  Because input, motion, targeting, and animation are already separate, adding
  abilities won't touch them — you only add the new system and route it through
  the same controller. That's the whole point of doing this split now.

  Suggested order of work

  Steps 1→2→3→4→5→6, testing after each. Start with PlayerAnimator (zero risk),
  end with the controller. Each step leaves the game playable, so you can commit
  between them.

  One decision worth making before you start: whether to wire the attack
  hit/finish via animation events (recommended — accurate, and you already use
  them) or keep the Invoke timers short-term. Want me to detail exactly how to
  add those two animation events to your attack clip in the Unity editor?
